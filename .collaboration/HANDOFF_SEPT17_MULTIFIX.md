## Unconditional self-review

Two real gaps were found and fixed in the candidate-equivalence capability (item 7) before it was considered done — both via the mandatory post-fix pass, not because anyone asked:

1. **Independence-discount bypass**: the equivalence-confirmation branch's rationale text initially said "independently confirmed" unconditionally, regardless of whether the two providers were actually declared distinct — bypassing the exact safeguard `CorroborationIndependenceTest` exists to enforce. The actual `VERIFIED`/`ARBITRATED` classification was never wrong (it's computed independently of this text, from `_independently_corroborated(corroboration)` directly), but the audit-trail wording was misleading for a same-provider case. Fixed to check `_independently_corroborated` exactly like the pre-existing literal-match branch does. Covered by `test_same_provider_equivalent_agreement_is_still_discounted`.
2. **More serious — a false-positive risk found live via the whole-pipeline harness, not by inspection**: both new call sites initially reused `coreference.action_relation_detail` unchanged, which tries a free wording/elaboration shortcut (`action_identity`'s exact-stemmed-set or subset match) needing no governed source at all, before ever consulting one. That shortcut is safe for a FACT's own description against ONE candidate's official descriptor (elaboration, never a merge risk since only one candidate is in play) but is **unsafe between two candidates' own official descriptors**: two authoritative code entries differing by exactly an added qualifying clause (an indication-clause suffix — the very F1/`AXIS_INDICATION_CLAUSE` axis from item 1 above) are BY DESIGN distinct, code-defining entries, not the same event elaborated. Running the existing indication-clause whole-pipeline regression scenario against the draft equivalence fix surfaced this directly: it started wrongly resolving `SAME_EVENT` via stemmed-subset wording alone, with no `procedure_relation` configured at all, which would have silently defeated the F1 axis. Fixed architecturally by splitting `action_relation_detail` into two functions — `governed_procedure_relation(left, right, source)` is the strict, source-backed-only half (no wording shortcut); `action_relation_detail` tries the wording shortcut first, then delegates to it (unchanged behavior for its existing fact-vs-candidate callers). Both new `resolution.py` call sites now call `governed_procedure_relation` directly. Covered by `GovernedProcedureRelationCandidateComparison` (4 new tests in `test_evidence_graph.py`), which pins the exact false positive found.
- Adjacent-instance check performed: confirmed no other existing caller of `action_relation_detail` compares two CANDIDATES to each other (all existing callers compare a fact/action description against one candidate or one other action phrase, the shape the wording shortcut is actually safe for) — the two new call sites in this range were the only ones needing the split.
- Checked the "prefer current/non-deprecated candidate" question directly (raised independently during review of this work): confirmed the risk of releasing a formally-retired code is already closed upstream, by `resolution._active_only` (drops any `Outcome.BLOCKED` candidate from the shortlist before verification) and the `code_active_on_dos` release gate as a backstop — neither of which this range touches. Confirmed the currently-loaded CPT data (`data/codes/cpt_codes.json`) carries no `status`/`effective_to`/`term_date`/replaced-by field at all, so a finer "prefer current over legacy-but-still-active" tie-break has no authoritative field to key on today; deliberately not implemented to avoid inventing a heuristic. `chosen` in the new mechanism is always the primary evaluator's own pick (corroboration only ever confirms or subtracts, per the pre-existing invariant) — flagging this as a known design property, not a defect, for reviewer awareness.
